# Полный гайд по изменениям сайта Istanbul

Дата: 4 октября 2026 года. Этот документ объясняет текущее состояние проекта, внесённые изменения и то, что нужно понимать на защите. Это учебное пояснение к реальному коду сайта.

## 1. Что мы делаем на midterm

Мы продолжаем существующий сайт ресторана Istanbul в Астане. Тема, команда и восемь страниц остались прежними. Задача — завершить структуру, связать страницы между собой, заполнить контент и подготовить HTML/CSS для следующих заданий с JavaScript.

Сейчас сайт умеет показывать страницы, переходить по ссылкам, открывать мобильную навигацию, проверять обязательные поля форм и показывать заранее подготовленный результат. Он не оформляет заказ, не бронирует стол, не отправляет вопрос или отзыв и не рассчитывает сумму автоматически.

Для midterm преподаватель разрешает не реализовывать JavaScript-поведение. Но поля, кнопки, сообщения, контейнеры и стили будущих состояний должны уже существовать. Поэтому в проекте подготовлены и интерфейс, и точки подключения для будущего кода.

В каждой шапке находятся одни и те же семь ссылок: Home, Menu, Visit, Gallery, About, FAQ, Feedback. По вашей просьбе Colophon убран из верхнего меню на всех страницах. Ссылка на него сохранена в footer, поэтому все восемь страниц доступны.

Подвал теперь одинаковый: логотип, адрес, телефон, авторы и ссылки на все страницы. Раньше набор ссылок менялся от страницы к странице.

Заголовки вкладок имеют общий шаблон:

```text
Menu — Istanbul Restaurant Astana
Visit — Istanbul Restaurant Astana
FAQ — Istanbul Restaurant Astana
```

Текущая страница отмечается атрибутом `aria-current="page"`. CSS выделяет именно её ссылку:

```css
.navbar .nav-link[aria-current="page"] {
  color: var(--brand-ink);
  text-decoration: underline;
  text-decoration-color: var(--brand-gold);
  text-underline-offset: .5em;
}
```

`.navbar .nav-link` выбирает ссылку внутри навигации. `[aria-current="page"]` уточняет, что правило применяется только к текущей странице. Такое оформление даёт посетителю ориентир, а атрибут сообщает ту же информацию программе чтения с экрана.

## 6. Bootstrap: что делает библиотека, а что делаем мы

Bootstrap — готовая библиотека CSS и компонентов. Она уже использовалась в версии, полученной из GitHub. Мы сохраняем её как основной инструмент раскладки.

Пример используемой сетки:

```html
<div class="container">
  <div class="row g-4">
    <div class="col-12 col-md-6 col-lg-4">
      <p>Содержимое карточки</p>
    </div>
  </div>
</div>
```

В Bootstrap строка делится на 12 условных колонок. `container` задаёт ширину и отступы основной области. `row` объединяет колонки. `g-4` создаёт промежутки. `col-12` занимает всю строку на маленьком экране; `col-md-6` — половину начиная с 768 px; `col-lg-4` — треть начиная с 992 px. Поэтому карточки меню показываются по одной, по две или по три в строке.

Другие классы, которые нужно узнавать:

| Класс | Значение |
| --- | --- |
| `py-5` | Отступы сверху и снизу |
| `p-4` | Внутренние отступы со всех сторон |
| `mt-4` | Отступ сверху |
| `d-flex` | Flexbox-контейнер |
| `flex-wrap` | Разрешить перенос элементов |
| `gap-2` | Промежутки между flex/grid-элементами |
| `btn btn-warning` | Кнопка с Bootstrap-оформлением; её цвет уточняют наши переменные |
| `btn btn-outline-dark` | Кнопка с тёмной рамкой |
| `form-control` | Оформление input/textarea |
| `form-select` | Оформление select |
| `img-fluid` | Изображение не превышает доступную ширину |
| `table-responsive` | Таблица при необходимости прокручивается внутри своего контейнера |
| `ratio ratio-4x3` | Область изображения с пропорциями 4:3 |

Bootstrap теперь загружается из `vendor/bootstrap`, а не из внешнего CDN. Сохранены официальные файлы версии 5.3.8; их SHA-384 совпал с исходными SRI-хешами в страницах. Код библиотеки не переписывался.

**Уточнение про JavaScript:** своего JavaScript для сайта мы не добавляли. Но готовый `bootstrap.bundle.min.js` существует и открывает/закрывает мобильное меню. Поэтому фраза «на сайте вообще нет JavaScript» была бы неточной. Правильно: «нет собственного JavaScript; Bootstrap использует свой готовый компонент навигации».

`mainNavbar` переименован в `main-navbar`. С ним согласованы `id`, `data-bs-target` и `aria-controls`, поэтому кнопка обращается к правильному меню.

## 7. Что изменилось в меню и откуда цены

В старом Menu было четырнадцать пустых элементов цены. Теперь отображается законченная подборка из шести категорий: Breakfast, Döner, Hot dishes, Pizza, Salads, Soups. В каждой по три блюда.

Цены взяты из опубликованного меню для Istanbul на Улы Дала, 56 с совпадающим телефоном. Источник и ограничения указаны в `docs/content-sources.md`. Это опубликованные справочные цены, а не обещание сегодняшней цены. Перед реальным заказом их нужно подтвердить у ресторана. Цены для старых непроверенных блюд мы не придумывали.

У элементов меню есть данные для будущего JS:

```html
<option value="four-seasons" data-price="3750">
  Four Seasons — 3,750 ₸
</option>
```

Текст — то, что видит посетитель. `value="four-seasons"` — короткое значение, которое попадёт в форму. `data-price="3750"` — числовая цена, которую будущий JS сможет прочитать. Сам по себе `data-price` ничего не вычисляет.

Количество порций задаётся так:

```html
<input
  class="form-control"
  id="menu-quantity"
  name="quantity"
  type="number"
  min="1"
  max="20"
  value="1"
  required
>
```

`type="number"` задаёт числовое поле. `min` и `max` ограничивают допустимые значения. `value="1"` задаёт начальное значение. `required` делает поле обязательным.

Для результата расчёта уже создан `output`:

```html
<output
  id="menu-total"
  for="menu-dish menu-quantity"
  class="d-block border rounded p-2"
  aria-live="polite"
>No estimate yet</output>
```

`for` показывает, с какими полями связан результат. Но браузер **не вычисляет сумму автоматически** из-за одного атрибута `for`. После выбора Four Seasons и одной порции здесь пока остаётся `No estimate yet`. В следующем задании JS сможет вычислить `3750 × 1`, обновить текст и показать выбранное блюдо в кратком описании.

## 8. Как работают формы сейчас — без нашего JavaScript

Все четыре формы используют один принцип: браузер проверяет обязательные поля, затем переход по `action` показывает готовый результат через CSS.

Вот реальные атрибуты формы Menu:

```html
<form
  id="menu-meal-form"
  action="menu.html#menu-plan-result"
  method="get"
  aria-describedby="menu-form-help"
>
```

`id` нужен для ссылок, CSS и будущего JS. `action` задаёт адрес перехода после успешной отправки. `method="get"` добавляет значения полей в адресную строку. `aria-describedby` связывает форму с её пояснением.

Кнопка:

```html
<button id="menu-submit" class="btn btn-warning" type="submit">
  Check meal choices
</button>
```

`type="submit"` запускает обычную отправку формы. До перехода браузер проверяет её ограничения. Если блюдо не выбрано или количество недопустимо, переход блокируется и браузер показывает своё сообщение.

Если выбрана Four Seasons и одна порция, получится адрес:

```text
menu.html?dish=four-seasons&quantity=1#menu-plan-result
```

Разбор адреса:

| Часть | Значение |
| --- | --- |
| `menu.html` | Страница, которую открываем |
| `?` | Начало параметров запроса |
| `dish=four-seasons` | Значение поля с `name="dish"` |
| `&` | Разделитель параметров |
| `quantity=1` | Значение поля с `name="quantity"` |
| `#menu-plan-result` | Идентификатор блока, к которому нужно перейти |

Параметры запроса передаются серверу, обслуживающему страницу; фрагмент после `#` используется браузером. Наш простой статический сайт не обрабатывает эти параметры как заказ и не сохраняет их в базу. При прямом открытии файлов вообще нет серверной обработки. Значения видны в URL; это не скрытое хранилище.

После перехода страница загружается заново. Её HTML не читает значения из URL и не подставляет их обратно в поля. Поэтому после проверки выбор может вернуться к исходному состоянию. Это текущая граница статической реализации.

Фрагмент делает секцию результата CSS-целью:

```css
.form-result { display: none; }
.result-panel:target .form-result { display: block; }
.result-panel:target .result-idle { display: none; }
```

До отправки внутри `result-panel` видна подсказка `result-idle`, а зелёный `.form-result` скрыт. Когда адрес содержит id этой панели, срабатывает `:target`: подсказка скрывается, зелёный блок появляется.

Сообщение заранее написано в HTML. Оно не содержит вычисленной суммы, реального номера заказа или ответа ресторана. Если вручную открыть адрес с таким `#`, блок тоже появится: CSS не проверяет факт отправки. Это подготовленное состояние интерфейса, а не защищённая квитанция.

| Страница | Форма | Конец локального сценария |
| --- | --- | --- |
| Menu | `menu-meal-form` | Выбор проверен; можно перейти к планированию визита |
| Visit | `visit-plan-form` | Поля визита проверены; можно посмотреть адрес и часы |
| FAQ | `faq-question-form` | Поля вопроса проверены; вопрос не отправлен |
| Feedback | `feedback-review-form` | Поля отзыва проверены; отзыв не опубликован |

Для Visit, FAQ и Feedback браузер также проверяет формат email и допустимые числовые значения. Проверка email означает проверку формата, а не существования почтового ящика. Поле `type="tel"` само по себе не доказывает правильность или существование телефонного номера. Проверка обязательной даты тоже не подтверждает наличие свободных столов.

Кнопки и ссылки имеют разные назначения:

- **Check…** — обычный `submit`: проверить ограничения полей и перейти к результату.
- **Reset fields** — `type="reset"`: вернуть поля текущей формы к исходным значениям из HTML. Это не удаление данных из базы и не сброс всей страницы. Если результат уже открыт через `#`, reset сам по себе не убирает этот фрагмент.
- **Start again** — ссылка на исходную страницу и форму без параметров результата. Она открывает начальное состояние и скрывает зелёный блок.
- **Plan your visit** — обычная ссылка на `visit.html#plan-visit`. Выбранное блюдо автоматически на другую страницу пока не переносится.
- **Call / WhatsApp / Public reviews** — отдельные внешние действия. Сайт не делает их за посетителя и ничего не отправляет автоматически.

## 10. `id`, `class`, `name` и `data-*`: важно не путать

| Атрибут | Для чего нужен | Пример |
| --- | --- | --- |
| `id` | Найти один конкретный элемент; создать якорь; связать подпись с полем | `id="menu-quantity"` |
| `class` | Применить общий стиль или состояние к нескольким элементам | `class="form-control"` |
| `name` | Задать имя значения при отправке формы | `name="quantity"` |
| `data-*` | Хранить дополнительные данные для будущего JS | `data-price="3750"` |

`id` должен быть уникален **в пределах одной страницы**. Один и тот же `main-navbar` на разных страницах допустим: это разные документы. Наши id используют английские слова в нижнем регистре через дефис.

Связь подписи и поля:

```html
<label for="visit-name" class="form-label">Name</label>
<input id="visit-name" name="name" type="text" required>
```

`for` у label совпадает с `id` поля. Нажатие на подпись переводит фокус в поле; программа чтения с экрана понимает его название. `placeholder` не заменяет label: подсказка исчезает после ввода.

## 11. Какие элементы подготовлены для JavaScript

На каждой форме имеются:

- id формы и каждого поля;
- id кнопок submit/reset;
- `<страница>-errors` для общего сообщения об ошибках;
- `<id-поля>-error` для сообщения рядом с конкретным полем;
- `<страница>-summary` для описания введённых данных;
- `<страница>-confirmation` для будущего динамического подтверждения;
- готовая секция результата.

Например, в Menu есть `menu-errors`, `menu-dish-error`, `menu-quantity-error`, `menu-summary`, `menu-confirmation` и `menu-plan-result`.

Пустой контейнер ошибки уже присутствует:

```html
<div
  id="menu-errors"
  class="is-hidden is-error p-3 mb-3"
  role="alert"
  tabindex="-1"
></div>
```

Сейчас он пуст и скрыт. В дальнейшем JS сможет записать туда понятный текст и убрать `is-hidden`. Это технический контейнер будущего состояния, а не пустой раздел страницы, который забыли заполнить.

Для будущего изменения списков подготовлены `generated-menu-items`, `generated-gallery-items`, `generated-faq-items` и `generated-reviews`. Существующие списки имеют свои id: `menu-items`, `gallery-items`, `faq-items`, `guest-reviews`.

`aria-live="polite"` позволяет программе чтения с экрана сообщить об обновлении, не прерывая текущее чтение. `role="alert"` обозначает важное сообщение об ошибке. `role="status"` подходит для результата действия. `tabindex="-1"` позволяет будущему JS переводить фокус на сообщение, не добавляя его в обычную последовательность Tab.

## 12. Общие CSS-состояния

| Класс | Как выглядит или действует | Будущее применение |
| --- | --- | --- |
| `.is-hidden` | `display: none` | Скрыть/показать сообщение или результат |
| `.is-active` | Жирный подчёркнутый текст | Активный фильтр или элемент |
| `.is-selected` | Золотая рамка и контур | Выбранное блюдо/карточка |
| `.is-error` | Красное оформление | Ошибка формы или поля |
| `.is-success` | Зелёное оформление | Успешно завершённое локальное действие |
| `.field-error` | Текст ошибки под полем | Пояснение, что исправить |

CSS описывает вид состояния. JS позже будет решать, когда добавить или убрать класс. Наличие `.is-error` не означает, что сейчас автоматически реализована вся логика ошибок. На этом этапе фактическую проверку обязательных полей выполняет браузер; наши контейнеры готовы для следующих заданий.

## 13. Остальные изменения в CSS

В `css/base.css` остаётся небольшая общая коррекция поверх Bootstrap.

**Палитра.** Переменные `--brand-ink`, `--brand-paper`, `--brand-gold`, `--brand-flame` задают цвета проекта. Например, `var(--brand-gold)` использует значение общей золотой переменной. Изменение этой переменной позволяет согласованно изменить все места, где она используется.

**Закреплённая шапка.** Ваше правило сохранено:

```css
.site-header {
  position: sticky;
  top: 0;
  z-index: 102;
}
```

`sticky` сохраняет шапку в обычном потоке, но при прокрутке удерживает её у верхней границы. `top: 0` задаёт эту границу. `z-index` помогает шапке отображаться над основным содержимым.

**Отступ для переходов по якорям.** `scroll-padding-top` и `scroll-margin-top` помогают не прятать заголовки под закреплённой шапкой при переходе к `#location-title` или результату формы.

**FAQ.** Ваш класс `.faq-stepss` сохранён. Его элементы имеют рамку, скругление и внутренние отступы. У списка `.faq-steps` добавлены общие промежутки. На небольших экранах отступ карточки уменьшается.

**Изображения.** `object-fit: cover` заполняет область без искажения пропорций, обрезая лишнее. Для логотипа используется `contain`, чтобы он был виден целиком. Для главной фотографии `::after` рисует тёмный градиент, чтобы текст был читаемее. `pointer-events: none` у градиента позволяет нажимать ссылки под ним.

**Клавиатура.** `:focus-visible` рисует заметный контур на ссылках, кнопках и полях. Skip link появляется при фокусе и ведёт к `#main-content`, позволяя пропустить навигацию.

**Узкие экраны.** `min-width: 0` у колонок позволяет содержимому сжиматься; перенос длинного текста помогает избежать переполнения. На ширине до 575.98 px логотип и отступы FAQ становятся меньше. Проблемы переполнения не маскируются общим `overflow-x: hidden` на всей странице.

## 14. Семантика HTML и что мы исправили

Семантический тег сообщает назначение блока:

| Тег | Назначение |
| --- | --- |
| `header` | Шапка |
| `nav` | Навигация |
| `main` | Основное содержимое |
| `section` | Тематический раздел с заголовком |
| `article` | Самостоятельная единица содержимого |
| `aside` | Дополнительная информация |
| `footer` | Подвал документа или блока |
| `figure` / `figcaption` | Иллюстрация и её подпись |
| `form` | Форма |
| `fieldset` / `legend` | Связанная группа полей и её название |
| `div` | Контейнер без отдельного смыслового назначения |

Некоторые `article`/`aside` использовались только как колонки раскладки и создавали предупреждения о разделах без собственных заголовков. Там, где блок не был самостоятельной статьёй или дополнением, контейнер заменён на `div`. Семантические теги в подходящих местах сохранены.

В FAQ отдельные вопросы теперь используют `h3`: заголовок всей страницы — `h1`, раздела вопросов — `h2`, каждого вопроса — `h3`. Размер внешнего вида можно задавать классом Bootstrap; он не требует менять логический уровень заголовка.

## 16. Что именно проверено

**Проверка исходников.** `tools/check_site.py` проверяет страницы, локальные файлы и якоря, уникальность id, ссылки label/ARIA, одинаковую навигацию и подвал, наличие form hooks, пустые цены и следы конфликтов Git.

**Валидатор.** Официальный Nu Html Checker 26.10.2 запущен локально. Все восемь страниц получили ноль ошибок и ноль предупреждений. HTML не отправлялся во внешний сервис. Отчёт: `docs/checks/w3c.json`.

**Браузер.** `tools/check_browser.cjs` запускает установленный Chrome через Playwright. Проверено 8 страниц на 3 ширинах: 1440, 390 и 320 px — 24 проверки раскладки. Ошибок консоли, загрузки изображений и горизонтального переполнения не найдено. Проверены открытие/закрытие мобильного меню, пустые и заполненные формы, неверный email, результат, начало заново, reset, клавиатурная skip link и три полных пути. Отчёт: `docs/checks/browser.json`.

**Скриншоты.** Есть 16 полноразмерных снимков — каждая из восьми страниц на компьютере и телефоне. Ещё четыре показывают результаты форм на телефоне. Итого 20. Список: `docs/screenshots/README.md`.

Автоматическая съёмка теперь ждёт декодирования фотографий и полного закрытия меню: иначе снимок мог поймать ещё не нарисованное изображение или промежуточную анимацию. Это исправление процедуры съёмки, а не замена настоящего сайта картинкой.

Эти проверки подтверждают локальную версию. Они не доказывают работу на каждом физическом телефоне, актуальность всех внешних сайтов или проведение командной взаимной проверки.

## 17. Как посмотреть и проверить изменения самому

Из папки проекта можно открыть `index.html`. Все основные ресурсы локальные. Для работы через браузерный адрес запустите сервер:

```powershell
python -m http.server 4173 --bind 127.0.0.1
```

Затем откройте `http://127.0.0.1:4173/index.html`. Если сервер уже запущен, второй на том же порту запускать не нужно.

Для просмотра изменения конкретного файла:

```powershell
git diff -- menu.html
git diff -- css/base.css
git status --short
```

`git diff` сравнивает текущие незакоммиченные изменения с `HEAD`. Он не показывает весь первоначальный переход на Bootstrap, потому что тот уже находится в коммите `b098e9e`. Новые непроиндексированные файлы из `docs`, `tools`, `vendor` тоже нужно открыть отдельно: обычный `git diff` их содержимое пока не показывает.

Проверка HTML-связей требует Python с `lxml`:

```powershell
python tools/check_site.py
```

Локальная валидация требует Java 17+ и официальный `vnu.jar`:

```powershell
python tools/check_w3c.py C:\path\to\vnu.jar
```

Браузерный скрипт требует уже установленный Playwright и Chrome; пути можно задать через `SITE_PLAYWRIGHT_MODULE` и `SITE_CHROME`. Самому сайту эти инструменты не нужны.

## 19. Что такое `midterm` tag

Коммит фиксирует набор файлов. Тег — имя, указывающее на определённый коммит. Тег `midterm` должен обозначить окончательные HTML и CSS, с которыми преподаватель сравнит будущие задания.

Он пока не поставлен: команда ещё должна проверить и принять структуру. После этой отметки новые элементы и новые стили по заданию должны создаваться через JavaScript.

После принятия финальной версии можно выполнить:

```powershell
git add .
git commit -m "Finish midterm HTML and CSS"
git tag -a midterm -m "Freeze midterm HTML and CSS"
git push feruum master:main
git push feruum midterm
```

Перед этим нужно посмотреть diff и убедиться, что выбран правильный remote. Здесь `master` отслеживает `feruum/main`. Команда push выше отправляет локальный `master` в удалённый `main`. Если Git сообщает о новых удалённых коммитах, сначала нужно согласовать изменения; force push для этого не нужен.

> Мы продолжаем сайт Istanbul. На midterm мы завершили общую структуру восьми страниц, сделали одинаковую навигацию и подвал, заполнили подборку меню опубликованными ценами, связали страницы тремя пользовательскими путями и подготовили формы, сообщения и CSS-состояния для будущего JavaScript.
